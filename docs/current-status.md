## What Just Happened

### Thread 17: ROM Transformation — From Theory to Working Demo

This session made more concrete technical progress than any previous session. Five CC experiments validated the core architectural approach for deep NES game modification.

**Experiment 1: SMB Transformation Toolkit (smb-api.cjs)**
Built an automated Game Genie — CC explored SMB's RAM, discovered addresses for player state, enemies, levels, physics values, and built a callable JavaScript API. 9/9 transformation tests passed: palette swaps, CHR tile replacement, sprite injection, physics modification (jump height), enemy speed control, invincibility, level warping, lives modification, death suppression. 18 minutes, ~$4.

**Experiment 2: PRG Disassembly Comprehension — SMB**
CC disassembled SMB's 32KB PRG-ROM from raw bytes and produced a fully annotated analysis: main loop, NMI handler, state machine, player physics (gravity at $B3D0, jump velocity table at $B432), entity system (6 slots at $AF03), enemy AI dispatch, level data format (compact 2-byte encoding, 34 areas in ~3.5KB), collision detection (bounding box at $BE70). Scored 10/10 on ground truth validation. Then wrote 13 bytes of new 6502 machine code making a Goomba chase Mario — injected at runtime, working perfectly. 18 minutes, ~$4.

**Experiment 3: PRG Disassembly Comprehension — Mega Man 2**
Same experiment on a harder target: 256KB PRG-ROM with MMC1 bank switching across 16 banks. CC disassembled all 16 banks, identified the full architecture (main loop in bank 14, NMI for PPU/sound only, bank switching IS the state machine, stage banks 0-7 map directly to stages 0-7). Scored 10/10 on ground truth validation INCLUDING catching two deliberately planted false facts. Validated runtime code injection on bank-switched ROM via rom.rom[bank][offset] patching. 18 minutes, ~$4.

**Experiment 4: Sprite Suppress-and-Replace**
Developed and validated the OAM suppression + canvas overlay approach for character replacement. Proved that Mario's sprites can be suppressed every frame while a replacement character is drawn at Mario's RAM-tracked position. Link from Zelda was successfully injected into SMB — recognizable, correctly positioned, interacting with the game world. The composition-to-decomposition tile mapping problem is sidestepped entirely: we don't use the game's tile mapping at all.

**Experiment 5: PixelLab → SMB End-to-End Pipeline**
Generated Harry Potter character sprites via PixelLab API (standing, walking, jumping, small/big/fire variants), rendered as canvas overlay on the running NES game. Harry Potter replaces Mario in Super Mario Bros: walks, jumps, grows on mushroom, changes color on fire flower, shoots fireballs. Game is fully playable. Walking animation frames need better PixelLab prompt tuning (init_image_strength too high, frames too similar), but the pipeline works end-to-end.

### Key Architectural Insights

**The Retroactively Constructed Modding API:** NES ROMs lack modding APIs, but Claude can read any game's compiled PRG-ROM, fully understand its architecture, and produce a game-specific API definition — human-readable function calls mapped to specific RAM/VRAM/OAM addresses. This is the central artifact the extraction pipeline should produce. Proven on SMB (NROM) and MM2 (MMC1 bank-switched).

**The Orchestrator as Third Processor:** The NES has CPU and PPU weaving together in a frame cycle. The Orchestrator hooks into that same cycle as a peer — reading game state from RAM, suppressing/modifying/adding content before each frame renders. Fast path (per-frame rules) handles real-time modifications; slow path (LLM calls on significant events) generates new directives.

**Canvas Overlay vs NES Tile Injection:** For visual replacement, rendering PixelLab sprites directly on the canvas at RAM-tracked positions is dramatically simpler and higher quality than converting to NES tile format. The NES handles all mechanics (physics, collision, AI, scrolling); the canvas handles all custom visuals. The game's PPU becomes the background renderer; the canvas becomes the foreground renderer.

**The Resource ROM:** A third ROM (alongside original PRG and CHR) that exists purely as a content library — new tile sheets, level data tables, entity parameters — generated by the LLM and structured for the emulator's read pathways. The Orchestrator routes reads from the original ROM to the resource ROM when substituting content.

**Platform Architecture Validated:**
- Universal layer (PPU-level, works on any ROM): OAM suppression, canvas rendering, palette manipulation
- Per-game layer (Claude PRG comprehension): RAM map, entity system, events, state machine, level data format
- Creative layer (PixelLab + LLM + CAS): visual generation, behavior authoring, social dynamics
